# 0.4.0 — The multi-byte NOP Rosetta cannot translate: one root cause behind both ACE and IL2CPP

Building on 0.3.0 (ACE kernel exports), this release finds and fixes the **actual
reason the game would not start on Apple silicon**.

Validated on: Apple M4 Pro, macOS 26.1, CrossOver 26.1, NIKKE 152.8.13 (global).

---

## 1. Root cause: Rosetta 2 cannot translate the register form of `0F 1F`

ACE reports "failed to load the driver", but **ACE is not the problem** — the
problem is that **Rosetta 2 does not support the register encoding of the
multi-byte NOP**.

Measured with a plain macOS x86_64 program, entirely outside Wine:

| Encoding | Meaning | Rosetta |
|---|---|---|
| `0f 1f 00` | `nop (rax)` | ✅ fine |
| `0f 1f 40 00` | `nop 0(rax)` | ✅ fine |
| `0f 1f 44 00 00` | `nop 0(rax,rax,1)` | ✅ fine |
| `66 0f 1f 44 00 00` | same, with a 66 prefix | ✅ fine |
| **`0f 1f c0`** | **`nop eax`** | ❌ **SIGILL** |
| **`0f 1f c1`** | **`nop ecx`** | ❌ **SIGILL** |
| **`41 0f 1f c0`** | **`nop r8d`** | ❌ **SIGILL** |
| **`41 0f 1f c1`** | **`nop r9d`** | ❌ **SIGILL** |
| **`41 0f 1f c7`** | **`nop r15d`** | ❌ **SIGILL** |
| `9c` / `9d` | `pushf` / `popf` | ✅ fine |

**The pattern: `0F 1F /0` fails to translate whenever the ModRM mod field is
`11` (the register form); the memory forms (mod ≠ 11) are fine.** The encoding
is a legal no-op on real Intel/AMD CPUs — the Intel manual's "Multi-byte NOP"
explicitly covers the register form — so **only the CPU emulator is at fault**.

### It breaks two different things at once

| Victim | Symptom | Faulting site |
|---|---|---|
| ACE kernel driver | Dialog "failed to load the driver, wait 30 seconds or restart" `(1-1720-1100215145)`; service returns `ERROR_GEN_FAILURE` | `.tvm0` section of `ACE-CORE102797.sys`, bytes `41 0F 1F C1` |
| Unity IL2CPP | `Fatal error / Failed to initialize IL2CPP` | user-mode `EXCEPTION_ILLEGAL_INSTRUCTION` |

The bytes in memory were verified to **match the file exactly** — there is no
self-decrypting or self-modifying code involved. It is an ordinary `nop r9d`.

## 2. The fix

Two places, both on the Wine side. **Neither game nor ACE files are modified.**

### 2.1 Kernel mode

`patches/crossover-26.1-ntoskrnl-rosetta-nop.patch`

Wine's ntoskrnl vectored handler exists to emulate privileged instructions for
drivers, but it **only handles `EXCEPTION_PRIV_INSTRUCTION` and does not handle
`EXCEPTION_ILLEGAL_INSTRUCTION` at all** — which is precisely what ACE raises.

`rosetta_nop_length()` decodes the prefixes, the `0F 1F /0` opcode and the
ModRM byte, advances RIP past the instruction and returns
`EXCEPTION_CONTINUE_EXECUTION`.

Unrecognised illegal instructions now log their **opcode bytes**, so the next
problem of this kind can be read out of a log instead of only seen as a crash.

### 2.2 User mode

`patches/crossover-26.1-rosetta-multibyte-nop.patch`

CrossOver already carries two Rosetta hacks in this exact spot:

```c
    case TRAP_x86_PRIVINFLT:   /* Invalid opcode exception */
#ifdef __APPLE__
        /* CW HACK 20186 */
        if (handle_cet_nop( ucontext, &context.c )) return;
        /* CW HACK 23427 */
        if (emulate_xgetbv( ucontext, &context.c )) return;
#endif
        rec.ExceptionCode = EXCEPTION_ILLEGAL_INSTRUCTION;
        break;
```

`handle_cet_nop` covers CET instructions and `emulate_xgetbv` covers XGETBV
("this will only take effect under Rosetta", per its own comment).
`handle_rosetta_nop()` follows the same pattern.

### 2.2.1 Relationship to the existing `nop_bridge`

**This repository already handled this encoding**, on the macOS side:
`nop_register_length()` in `src/nop_decode.h` covers exactly `0F 1F /0` with
`ModRM.mod == 3` (optionally REX.B), and `src/bridge.c` intercepts SIGILL and
emulates it, injected via `DYLD_INSERT_LIBRARIES`.

The new user-mode `handle_rosetta_nop()` covers **the same encoding**; only the
location differs — one on the macOS side, one inside Wine's ntdll. Two points
need stating plainly:

- **The kernel-mode patch is new and is the one that mattered.** With a normal
  launch through `open` (Info.plist applied, dylib injected) the ACE dialog
  still appeared; `ACE-CORE102797` only moved from `STOPPED` to `RUNNING` after
  the kernel-mode patch. The macOS-side `nop_bridge` therefore did not cover the
  driver's illegal-instruction path.
- **Whether the user-mode patch is necessary has not been isolated on this
  machine.** What was observed: `Failed to initialize IL2CPP` still occurred
  when launching through `open` (dylib active), and recovery happened in a
  direct launch (`DYLD_INSERT_LIBRARIES` unset) with the user-mode patch
  applied. Those two variables moved together, so nothing can be concluded
  about whether the dylib is active inside the game process. Settling it needs
  one more run with the bridge active and the user-mode patch removed.
- Consequently: **treat the kernel-mode patch as required, and the user-mode
  one as optional for now.** They coexist safely — whichever matches first
  handles the instruction, and it is never skipped twice.

### 2.3 Stubs the ACE CORE drivers need

`patches/crossover-26.1-ace-core-driver-stubs.patch`

Also implements the **10 stubs** imported by `ACE-CORE.sys` / `ACE-CORE.sys2`.
A Wine stub raises `EXCEPTION_WINE_STUB` (`EXCEPTION_NONCONTINUABLE`); the
drivers' own SEH catches it, `DriverEntry` fails and the service start returns
`ERROR_GEN_FAILURE`.

| Function | Approach |
|---|---|
| `ExQueueWorkItem` | Wine has no kernel worker threads; run on a dedicated thread so the work stays asynchronous |
| `KeInsertQueueApc` | Wine does not deliver kernel APCs; report the APC as not queued |
| `MmAllocateMappingAddress` / `MmFreeMappingAddress` | Allocate and release pool memory |
| `MmFreeContiguousMemory` | No-op: Wine's `MmAllocateContiguousMemory*` all return NULL |
| `IoGetTopLevelIrp` / `IoGetLowerDeviceObject` | Return NULL (Wine keeps no downward pointer) |
| `PsIsThreadTerminating` | Return FALSE |
| `RtlWalkFrameChain` | Reuse ntdll's `RtlCaptureStackBackTrace` |
| `SeCaptureSecurityDescriptor` | Copy per `RtlLengthSecurityDescriptor` |

Same principle as 0.3.0: **do not turn a failed query into a fake success.**
Unsupported paths say so explicitly.

## 3. A build detail you need to know

`ntdll.so` is a **Unix** library and builds as **arm64** by default, while the
bootstrap and every runtime are **x86_64**. The architecture mismatch is
rejected outright:

```
bootstrap: dlopen(...): mach-o file, but is an incompatible architecture
           (have 'arm64', need 'x86_64')
```

It has to be built for x86_64 separately, and **without `-DIS_WOW64_BUILD`**
(that describes the WoW64 host side; we want a native 64-bit ntdll):

```bash
rm -f dlls/ntdll/unix/*.o dlls/ntdll/ntdll.so
make dlls/ntdll/ntdll.so \
  CC="clang -arch x86_64" OBJC="clang -arch x86_64" \
  CFLAGS="-g -O2 -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0"
lipo -info dlls/ntdll/ntdll.so   # must report x86_64
```

`scripts/build_wine_modules.py` now performs this step, deleting any
host-architecture `dlls/ntdll/unix/*.o` first so `make` cannot skip the rebuild
as already up to date.

## 4. Install location (important)

The patches must be installed where **`WINEDLLPATH` points**, or they are never
loaded:

```bash
RT=local/runtime-modules/lib/wine
cp .../ntoskrnl.exe $RT/x86_64-windows/ntoskrnl.exe
cp .../ntdll.so     $RT/x86_64-unix/ntdll.so
```

**Also: Wine reuses an already-running `winedevice.exe` to load drivers.** After
replacing `ntoskrnl.exe` you must stop `services.exe` / `winedevice.exe` so they
are recreated, otherwise the old code keeps running from memory — which looks
exactly like "the patch did nothing".

**Install the build output as-is; do not re-sign it.** The built `ntdll.so` is
unsigned and loads fine from that path. Adding an ad-hoc signature on the macOS
side was tried here and produced `library load disallowed by system policy`,
which is strictly worse; replacing the file with `rm` + `cp` (a new inode)
rather than overwriting in place also avoids the kernel caching a stale
signature for the path. All of that is macOS-side and **needs no adjustment**.

## 6. New diagnostic tool

`tests/nkwin2.c` (`make build/nkwin2.exe`)

Enumerates windows, reads their text and injects clicks from inside the prefix.
Two properties make it irreplaceable:

1. **Window text is emitted with every non-ASCII character escaped as
   `\uXXXX`**, so CJK survives a pipe intact. Under Wine a MessageBox's Chinese
   text renders as boxes because of font fallback — the dialog reading
   "failed to load the driver" was completely invisible until the text was read
   directly, and **without that sentence the driver could not have been
   implicated, and the NOP could not have been found**.
2. **Synthetic input has to come from inside the prefix.** Driving a Wine window
   from macOS requires the Accessibility permission that both AppleScript and
   CGEvent are denied, so `autoclick` injects with `SendInput`.

| Command | Purpose |
|---|---|
| `nkwin2 list` | enumerate all top-level and child windows |
| `nkwin2 autoclick <x> <y> <sec>` | click screen (x,y) and poll for a `#32770` dialog |
| `nkwin2 clickabs <x> <y>` | click screen (x,y) with SendInput |

**reproduce the current source byte for byte**.
