# 0.4.0 — Rosetta 不支持的多字节 NOP：ACE 驱动与 IL2CPP 的同一个根因

在 0.3.0（ACE 内核导出补全）基础上，找到并修掉了**苹果芯片上游戏进不去的真正根因**。

本机验证环境：Apple M4 Pro、macOS 26.1、CrossOver 26.1、NIKKE 152.8.13 国际服。

---

## 一、根因：Rosetta 2 无法翻译 `0F 1F` 的寄存器形式

ACE 报的错是「无法加载驱动程序」，但**问题不在 ACE**，而在于
**Rosetta 2 不支持多字节 NOP 的寄存器编码形式**。

用一个纯 macOS x86_64 程序（完全不经过 Wine）单独测各种 NOP 编码：

| 编码 | 含义 | Rosetta 结果 |
|---|---|---|
| `0f 1f 00` | `nop (rax)` | ✅ 正常 |
| `0f 1f 40 00` | `nop 0(rax)` | ✅ 正常 |
| `0f 1f 44 00 00` | `nop 0(rax,rax,1)` | ✅ 正常 |
| `66 0f 1f 44 00 00` | 同上（带 66 前缀） | ✅ 正常 |
| **`0f 1f c0`** | **`nop eax`** | ❌ **SIGILL** |
| **`0f 1f c1`** | **`nop ecx`** | ❌ **SIGILL** |
| **`41 0f 1f c0`** | **`nop r8d`** | ❌ **SIGILL** |
| **`41 0f 1f c1`** | **`nop r9d`** | ❌ **SIGILL** |
| **`41 0f 1f c7`** | **`nop r15d`** | ❌ **SIGILL** |
| `9c` / `9d` | `pushf` / `popf` | ✅ 正常 |

**规律：`0F 1F /0` 只要 ModRM 的 mod 字段为 `11`（寄存器形式）就无法翻译；
内存形式（mod ≠ 11）完全正常。** 这条编码在真实 Intel/AMD CPU 上是合法的
NOP（Intel 手册 "Multi-byte NOP" 明确包含寄存器形式），**只有模拟器有问题**。

### 它同时卡死了两件事

| 受害者 | 表现 | 崩溃点 |
|---|---|---|
| ACE 内核驱动 | 弹窗「无法加载驱动程序，请等待30秒或重启系统之后再次尝试。(1-1720-1100215145)」，服务返回 `ERROR_GEN_FAILURE` | `ACE-CORE102797.sys` 的 `.tvm0` 节，字节 `41 0F 1F C1` |
| Unity IL2CPP | `Fatal error / Failed to initialize IL2CPP` | 用户态 `EXCEPTION_ILLEGAL_INSTRUCTION` |

已确认内存中的字节与文件中的字节**完全一致**，不存在自解密或自改代码——
就是一条普通的 `nop r9d`。

## 二、修复

两处，都是 Wine 侧，**不修改游戏和 ACE 目录**。

### 2.1 内核态

`patches/crossover-26.1-ntoskrnl-rosetta-nop.patch`

Wine 的 ntoskrnl vectored handler 本来就是用来给驱动模拟特殊指令的，
但它**只处理 `EXCEPTION_PRIV_INSTRUCTION`，完全没处理
`EXCEPTION_ILLEGAL_INSTRUCTION`**（正好是 ACE 抛出的那个）。

新增 `rosetta_nop_length()`：解析前缀 + `0F 1F /0` + ModRM 算出指令长度，
把 RIP 推过去并返回 `EXCEPTION_CONTINUE_EXECUTION`。

顺带把未识别的非法指令改成打印**操作码字节**，以后再遇到同类问题可以直接
从日志读出是哪条指令，而不用只能看到崩溃。

### 2.2 用户态

`patches/crossover-26.1-rosetta-multibyte-nop.patch`

CrossOver 自己已经有两个针对 Rosetta 的 hack：

```c
    case TRAP_x86_PRIVINFLT:   /* Invalid opcode exception */
#ifdef __APPLE__
        /* CW HACK 20186 */
        if (handle_cet_nop( ucontext, &context.c )) return;
        /* CW HACK 23427 */
        if (emulate_xgetbv( ucontext, &context.c )) return;
#endif
        rec.ExceptionCode = EXCEPTION_ILLEGAL_INSTRUCTION;
        break;
```

`handle_cet_nop` 处理 CET 指令，`emulate_xgetbv` 处理 XGETBV（注释里写着
"this will only take effect under Rosetta"）。照着同样的风格加了
`handle_rosetta_nop()`。

### 2.2.1 与仓库既有 `nop_bridge` 的关系

**本项目原本就已经处理过这条编码**，走的是 macOS 侧：
`src/nop_decode.h` 的 `nop_register_length()` 覆盖的正是
`0F 1F /0` 且 `ModRM.mod == 3`（可选 REX.B），由
`src/bridge.c` 拦截 SIGILL 后模拟，靠 `DYLD_INSERT_LIBRARIES` 注入。

本次新增的用户态 `handle_rosetta_nop()` 与它**覆盖同一条编码**，区别只在
实现位置：一个在 macOS 侧、一个在 Wine 的 ntdll 里。需要说明的是：

- **内核态那条是新的、也是关键的。** 通过 `open` 正常启动（Info.plist 生效、
  dylib 已注入）时，ACE 弹窗依然出现；只有打上内核态补丁后
  `ACE-CORE102797` 才从 `STOPPED` 变成 `RUNNING`。说明 macOS 侧的
  `nop_bridge` 没有覆盖到驱动的非法指令路径。
- **用户态那条是否必要，本机尚未做隔离验证。** 观察到的现象是：
  通过 `open` 启动（dylib 生效）时仍出现 `Failed to initialize IL2CPP`；
  而在直连启动（`DYLD_INSERT_LIBRARIES` 未设置）并打上用户态补丁后恢复正常。
  这两种情况混在一起，无法据此断定 dylib 在游戏进程里是否生效。
  需要在 `nop_bridge` 生效的前提下单独关掉用户态补丁再测一次，才能定论。
- 因此：**内核态补丁建议默认启用；用户态补丁目前作为可选项保留**，
  两条都可以安全共存（先命中的那条生效，不会重复跳过指令）。

### 2.3 ACE CORE 驱动需要的 stub

`patches/crossover-26.1-ace-core-driver-stubs.patch`

顺便把 `ACE-CORE.sys` / `ACE-CORE.sys2` 导入的 **10 个 stub** 补成真实实现。
Wine 的 stub 会抛 `EXCEPTION_WINE_STUB`（`EXCEPTION_NONCONTINUABLE`），
驱动自己的 SEH 接住后 `DriverEntry` 失败，服务启动返回 `ERROR_GEN_FAILURE`。

| 函数 | 实现方式 |
|---|---|
| `ExQueueWorkItem` | Wine 无内核工作线程，用独立线程执行，保持异步语义 |
| `KeInsertQueueApc` | Wine 不投递内核 APC，返回未入队 |
| `MmAllocateMappingAddress` / `MmFreeMappingAddress` | 分配/释放池内存 |
| `MmFreeContiguousMemory` | Wine 的 `MmAllocateContiguousMemory*` 一律返回 NULL，故为空操作 |
| `IoGetTopLevelIrp` / `IoGetLowerDeviceObject` | 返回 NULL（Wine 不维护向下指针）|
| `PsIsThreadTerminating` | 返回 FALSE |
| `RtlWalkFrameChain` | 复用 ntdll 的 `RtlCaptureStackBackTrace` |
| `SeCaptureSecurityDescriptor` | 按 `RtlLengthSecurityDescriptor` 复制一份 |

设计原则与 0.3.0 一致：**不把查询失败的接口伪装成成功值**，不支持的路径
明确返回"不支持"。

## 三、一个必须知道的构建细节

`ntdll.so` 是 **Unix 库**，本机默认编译出来是 **arm64**，
而 bootstrap 与所有运行时都是 **x86_64**，架构不符会被 bootstrap 直接拒绝：

```
bootstrap: dlopen(...): mach-o file, but is an incompatible architecture
           (have 'arm64', need 'x86_64')
```

必须按 x86_64 单独构建，并且**去掉 `-DIS_WOW64_BUILD`**（那是 WoW64 宿主侧的
描述，我们要的是原生 64 位 ntdll）：

```bash
rm -f dlls/ntdll/unix/*.o dlls/ntdll/ntdll.so
make dlls/ntdll/ntdll.so \
  CC="clang -arch x86_64" OBJC="clang -arch x86_64" \
  CFLAGS="-g -O2 -U_FORTIFY_SOURCE -D_FORTIFY_SOURCE=0"
lipo -info dlls/ntdll/ntdll.so   # 必须显示 x86_64
```

`scripts/build_wine_modules.py` 已接入这一步，并会先删掉宿主架构的
`dlls/ntdll/unix/*.o`，避免 `make` 因为"已是最新"而跳过重建。

## 四、安装位置（关键）

补丁必须装到 **`WINEDLLPATH` 指向的目录**，否则不会被加载：

```bash
RT=local/runtime-modules/lib/wine
cp .../ntoskrnl.exe $RT/x86_64-windows/ntoskrnl.exe
cp .../ntdll.so     $RT/x86_64-unix/ntdll.so
```

**另外：Wine 会复用已在运行的 `winedevice.exe` 来加载驱动。**
改完 `ntoskrnl.exe` 后必须把 `services.exe` / `winedevice.exe` 结束掉让它重建，
否则内存里跑的还是老代码——这一点会让人误判成"补丁没生效"。

**安装时保持构建产物原样，不要重新签名。** 构建出的 `ntdll.so` 是未签名的，
放在该路径下可以正常加载。本机实测过给它在 macOS 侧补 ad-hoc 签名，结果是
`library load disallowed by system policy`，反而不能加载；换文件时用
`rm` + `cp`（新 inode）而不是原地覆盖，也可以避免内核缓存住旧签名的报错。
这些都属于 macOS 侧，**不需要也不应该去调整**。

**未验证 / 遗留：**

- ⚠️ `ACE-CORE202797` 仍为 `STOPPED`（`sc start` 返回 `87 ERROR_INVALID_PARAMETER`）。
  它是另一类错误（不是指令问题），**且不影响进游戏**。
- ⚠️ 开场动画解码会在 `Player.log` 里刷一条 `E_NOTIMPL`：

  ```
  WindowsVideoMedia error 0x80004001 while reading
    .../StreamingAssets/install_mov_wide.mp4
  Context: Failed getting shared handle from IDXGIResource
  ```

  这是 Unity 的 WindowsVideoMedia 走 Media Foundation 的 DXGI 路径失败，
  `0x80004001` 是 `E_NOTIMPL`，**由本补丁的 `NOP_BRIDGE_MF_NO_DXGI` 分支产生**。

  > **2026-09-26 后续更正：这条结论下得太宽。** 进大厅时它确实不致命，
  > 但**进入剧情播片（`StoryEvent`）会把游戏卡死**——进程存活、单核 100%
  > 空转、`Player.log` 静默（实测 206 秒），必须强制结束。
  > 原因是 `NOP_BRIDGE_MF_NO_DXGI=1` **单独设置是个半配置状态**：
  > Unity 拿不到 device manager 而退到软件回退，reader 侧却仍按 D3D 帧预期工作。
  > 补上配对的 `NOP_BRIDGE_MF_SOFTWARE=1` 后问题消失。
  > 详见 [真正在用的技术](APPLIED-TECHNIQUES.zh-CN.md) 第 5.3 节。
- ⚠️ 未做长期稳定性测试。

## 六、新增诊断工具

`tests/nkwin2.c`（`make build/nkwin2.exe`）

在 prefix 内枚举窗口、读取窗口文字、注入点击。两件事让它不可替代：

1. **窗口文字按 `\uXXXX` 转义输出**，中文和控制字符能完整穿过管道。
   Wine 下 MessageBox 的中文因字体回退渲染成方块，那个写着
   「无法加载驱动程序」的弹窗在此之前是完全看不见的——**读不出这句话
   就不可能定位到驱动，也就不可能定位到 NOP**。
2. **合成输入必须来自 prefix 内部**。从 macOS 驱动 Wine 窗口需要辅助功能
   权限，AppleScript 与 CGEvent 都被拒，所以 `autoclick` 用 `SendInput` 注入。

| 命令 | 作用 |
|---|---|
| `nkwin2 list` | 列出全部顶层窗口与子窗口 |
| `nkwin2 autoclick <x> <y> <sec>` | 点击屏幕坐标并轮询捕获 `#32770` 对话框 |
| `nkwin2 clickabs <x> <y>` | 用 SendInput 点击屏幕坐标 |
